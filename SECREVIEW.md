# Security Code Review — hpc-workspace-v2

Reviewed: 2026-10-11 (`src/`, `bin/`, install rules; read-only review, no code changed).

## Threat model

`ws_allocate` and `ws_release` are installed privileged with `CAP_DAC_OVERRIDE+CAP_CHOWN+CAP_FOWNER` (or SUID root), `ws_restore` with `CAP_DAC_OVERRIDE+CAP_DAC_READ_SEARCH+CAP_FOWNER` (since the M6 fix; `src/setcap_install.cmake`). Authorization is therefore enforced in *userspace*, and user-controlled strings (workspace id, `-u` username, `-m` mail address, `~/.ws_user.conf`, user-owned directory trees) flow into root-privileged file operations. That is where the risk concentrates.

## High

### H1. DB entry write follows symlinks; `WsID` is never sanitized → arbitrary file truncate/chmod/chown — **FIXED** (src/dbv1.cpp)

`DBEntryV1::writeEntry` opens the DB file with plain `ofstream` (`src/dbv1.cpp:980`) — `O_CREAT|O_TRUNC` with symlink following, no `O_NOFOLLOW`/`O_EXCL` — and `chmod`/`chown` (`src/dbv1.cpp:998`, `src/dbv1.cpp:1011`) re-resolve the path while `CAP_DAC_OVERRIDE`/`CAP_FOWNER`/`CAP_CHOWN` are raised. The DB *filename* comes from an `id` that is concatenated verbatim into a path (`src/dbv1.cpp:315-317`, `src/dbv1.cpp:328-330`) with no check for `/` or `..`. The `name` is regex-validated, but **`-u` is not**: the extend path builds `dbid = user_option + "-" + name` for *any* caller (`src/ws_allocate.cpp:441`, unlike the root-gated `src/ws_allocate.cpp:455`). A user can point `dbid` at a file in a directory they own, pass the read/parse stage, swap it for a symlink before the (later) write, and get an arbitrary file truncated/overwritten with partially attacker-controlled YAML content, plus `chmod 0644` and `chown dbuid`.

*Fix applied: (a) a `checkID()` guard in the DB layer rejects empty, `.`, `..`, and any id containing `/` at `readEntry()`, `deleteEntry()`, and the `DBEntryV1` ctor — so `dbfilepath`'s parent is always exactly the (root-owned) database dir; (b) `writeEntry()` now opens the entry with raw `::open(O_WRONLY|O_CREAT|O_TRUNC|O_NOFOLLOW|O_CLOEXEC)` and applies `fchmod`/`fchown` on that fd, so the path is never re-resolved after the open and a planted symlink fails the open (ELOOP) instead of being truncated. Charset validation of ids is deliberately kept lenient (no `/`-and-dot rule only) to not break existing LDAP/AD usernames.*

### H2. `rmtree` family: double-close of fds, uninitialized `stat` on error path, fragile `dirent` caching — **FIXED** (src/utils.cpp)

- `rmtree_fd` calls `closedir()` (`src/utils.cpp:824`), which closes `topfd`, then every caller calls `close(dirfd)` again (`src/utils.cpp:537`, `src/utils.cpp:582`, `src/utils.cpp:800`) → systematic double-close. In the long-lived, multi-threaded root `ws_expirer`/`ws_stat` (thread pools, curl sockets), a recycled fd number can close an unrelated descriptor. `rmtree_below` even always double-closes (missing `dirfd_closed = true`, `src/utils.cpp:579-585`).
- If the initial `fstatat` fails it only logs (`src/utils.cpp:526-529`, `src/utils.cpp:571-574`) and then evaluates `S_ISDIR` on an **uninitialized** `orig_stat` — UB on exactly the error paths (e.g. restore of a 0700 `deleted` dir).
- `rmtree_fd` stores `dirent*` pointers from successive `readdir()` calls and uses them after the loop (`src/utils.cpp:770-782`). This only works as long as glibc's internal getdents buffer isn't refilled — fine for small dirs (hence the passing unit test at `tests/utils_test.cpp:37`), but for large directories (entries spanning multiple read chunks — realistic for HPC scratch dirs) earlier pointers alias stale data, so entries get deleted twice or missed entirely. Deletion correctness/retention guarantees of the root expirer depend on non-portable allocator behavior.
- `unlinkat(0, path, AT_REMOVEDIR)` (`src/utils.cpp:541`) resolves against fd 0 (stdin!) unless the path is absolute — only works by accident; the code's own FIXME says as much.

*Fix applied: `rmtree`/`rmtree_below`/`rmtree_fd` in `src/utils.cpp` were rewritten. (a) `rmtree_fd()` now has explicit fd-ownership semantics — it always closes `topfd` before returning (deadline, `fdopendir` failure, and normal `closedir()` paths), and the callers no longer `close()` it again, eliminating the double-close. (b) A failed `fstatat`/`openat` in `rmtree`/`rmtree_below` now logs and `return 0`s instead of falling through to `S_ISDIR` on an uninitialized `orig_stat`. (c) Directory entries are collected into a `std::vector<std::pair<std::string, unsigned char>>` (name + `d_type` by value) during the `readdir()` loop and processed afterwards, so no `dirent*` outlives the buffer refill. (d) All path-relative syscalls now use `AT_FDCWD` instead of the bogus dirfd `0`, and `DT_UNKNOWN` (`d_type` unsupported, e.g. NFS) falls back to an `fstatat`. The public API (`utils::rmtree`/`rmtree_below` signatures and return semantics) is unchanged; all callers (`ws_expirer`, `ws_release`, `ws_restore`) are unaffected.*

### H3. `ws_expirer` parses user-controlled data as root with no guards → crash stops all expiration — **FIXED** (src/ws_expirer.cpp, src/utils.cpp, src/user.cpp)

For each expiring workspace it reads the owner's `~/.ws_user.conf` while still fully privileged: `user::getUserhome` wraps `getpwnam()` in `gsl::not_null` (`src/user.cpp:71-74`) — a deleted-but-still-expiring user (routine on HPC sites) aborts the run; `utils::getFileContents` has no size cap (`src/utils.cpp:96-104`); `UserConfig(...)` can throw on malformed YAML and the per-filesystem loop has no catch (`src/ws_expirer.cpp:663-679`). Any of these kills expiration for all remaining entries/filesystems — a data-retention violation triggered by user-owned content. The `is_symlink`/`is_regular_file` checks also TOCTOU into the later open.

*Fix applied: (a) `user::getUserhome(username)` no longer wraps `getpwnam()` in `gsl::not_null` — it returns `""` for unknown users (the expirer was the only caller of the 1-arg form) and the expirer logs + falls back to filesystem defaults. (b) New `utils::readFileNoFollow(filename, maxSize=1 MiB)` opens with `O_NOFOLLOW|O_NONBLOCK|O_CLOEXEC`, checks `S_ISREG` *after* the open (kills the TOCTOU and the symlink-following `ifstream`), and bounds the read to `maxSize` — used by the expirer for `~/.ws_user.conf`; a fifo can no longer hang the privileged reader, and an oversize file throws instead of exhausting memory. (c) The whole expiration-mail block in `expire_workspaces` is wrapped in `try/catch (const std::exception&)`: the entry is already expired+renamed before the mail step, so any throw (YAML parse, read error) now logs and continues with the next entry; the `exit(-1)` on a symlinked user conf became a logged fallback to filesystem defaults. Unit test `readFileNoFollow` added to `tests/utils_test.cpp`. The reminder-mail path reads only root-owned DB fields, so it needed no guard.*

### H4. Race: freshly allocated workspace can be deleted by the expirer in the same run — **FIXED** (src/ws_expirer.cpp)

The expirer scans space dirs *before* snapshotting the DB (`src/ws_expirer.cpp:390-404` vs `src/ws_expirer.cpp:446`), while `ws_allocate` creates the directory before the DB entry. A workspace created between the two reads looks like a stray, gets moved to `deleted/` and then `rmtree`'d in the same run (phase 3). The developer's own FIXME documents it (`src/ws_expirer.cpp:470-471`, "dangerous with datarace #87"). A user hammering `ws_allocate` during an expirer run can lose a brand-new workspace. Related: stray-detection matches by *basename* across spaces (`src/ws_expirer.cpp:465-466`), so a name collision in another space protects a stray forever (quota leak) and classification rests on cross-space name uniqueness rather than path equality.

*Two clock-independent grace guards, no protocol change — implemented in `src/ws_expirer.cpp`:*

1. *Guard 1, the stray move: a stray candidate is `lstat`ed and skipped when its `st_mtime` (kernel-set on the storage server, not forgeable by the user during the allocation window) is younger than `STRAY_GRACETIME` — a file-local constant of 3600 s, deliberately not a config option. `mtime` alone, not `max(mtime, ctime)`, so tests can backdate with `touch -m` (`ctime` is not settable). The race victim's directory was created milliseconds-to-seconds before the scan, so it is always skipped; a genuinely orphaned directory (crashed `ws_allocate`) still gets cleaned, just one cycle later.*
2. *Guard 2, the same-run truncation: `run_start` is captured at the top of `clean_stray_directories`, and no `deleted/` directory whose trailing `-<digits>` move timestamp (embedded by the move in guard 1's block, parsed by a local `trailing_timestamp()` helper mirroring `splitExpiredId`: digit-only and plausibility-bounded) is ≥ `run_start` is `rmtree`d. Directories this run just moved over stay in `deleted/` until the next run, when the late-arriving DB entry protects them. This turns the developer's open FIXME question ("Is this intended?", datarace #87 — removed) into an explicit no.*

*Both guards sit after the existing "stray workspace"/"stray removed workspace" warnings, so log-based monitoring and bats assertions keep working; `bats/test/ws_expirer.bats` "clean stray directories" now backdates `stray-dir` with `touch -m -d "2000-01-01"` to exercise the actual move.*

### H5. `ws_share` and `ws_extend` have swapped contents — and are installed as-is — **RESOLVED** (not reproducible in current tree)

`bin/ws_extend` is the full ACL-sharing script (its own comments/usage say "ws_share"), `bin/ws_share` is the 15-line extend wrapper around `ws_allocate -x` (`bin/ws_share:5`). `CMakeLists.txt:209-213` installs both **without `RENAME`**, so every installed binary contradicts both man pages: `ws_share myws 10` silently *extends* (consuming a privileged tool's extension quota), while documented share invocations against the installed names no-op with exit code 0 (the usage branch of `bin/ws_share` never `exit 1`s).

*Re-verified 2026-10-12: in the current tree `bin/ws_extend` **is** the 15-line `ws_allocate -x` wrapper and `bin/ws_share` **is** the ACL share script — both match their names, both man pages and `bats/test/ws_share.bats`; the install rule (`CMakeLists.txt:209-213`) is therefore correct. The review's own line citations (`bin/ws_share:5` for the wrapper's `ws_allocate -x` line, the usage branch exiting 0) match current `bin/ws_extend:5,13-15` exactly, so the two file labels were transposed — either a review labeling error, or a real swap that was fixed in this working tree afterwards (`bin/ws_share_gemini.sh`, `bin/ws_share_orig` indicate a later share-script rework; confirm with `git log --oneline -- bin/`). Residual defect fixed: the `bin/ws_extend` usage branch now `exit 1`s. The option-injection half remains tracked in M7.*

## Medium

### M1. Per-user quota counts everyone's workspaces — **FIXED** (src/ws_allocate.cpp:341)

`countWorkspaces` (`src/ws_allocate.cpp:317`) ignored its `username` argument: `matchPattern("*", "*", ...)` composes filepattern `*-*` (`src/dbv1.cpp:298`) — once the *cluster-wide* count passes `maxuserworkspaces`, all users are locked out ("too many workspaces, exceeding global user limit", `src/ws_allocate.cpp:401-407`). Either a trivially-mountable availability attack or a config-policy surprise (the error message says "global user limit", so intent is ambiguous — but the function doc says "count workspaces of user").

*Fix applied: quota check now matches only the caller's entries (`username-*`), and the error message reflects the per-user limit. Kept the `too many workspaces` prefix asserted by `bats/test/ws_allocate.bats`.*

### M2. Extending a foreign workspace: weak authz + silent mail redirection — **FIXED** (src/ws_allocate.cpp)

The `-x -u` path (`src/ws_allocate.cpp:440-443`) has no root gate; the only check for non-owners is `access(wsdir, R|W|X)` (`src/ws_allocate.cpp:498-505`) — plain POSIX bits, not the workspace ACL/intent model. A group member can burn the owner's `maxextensions` and, via `-m`, **overwrite the victim's stored mail address** (`src/ws_allocate.cpp:512-514`), quietly redirecting all future expiration/reminder mails (which disclose workspace id, fs, expiry) to themselves. Also note `-u` is never regex-validated here (only `name` is).

*Fix applied ("extend in behalf of the owner", per `man 1 ws_allocate`): (a) a foreign non-root extend no longer applies the caller's `-m`/`-r`/`-c` (nor the mail auto-filled from the caller's `~/.ws_user.conf`) — the owner's stored mail, reminder and comment are kept; only the expiration is extended (an info line "extending in behalf of the owner: keeping owner's mail, reminder and comment" is logged). Owner and root paths are unchanged. (b) The authorization gate now enforces the documented `-u` precondition: the workspace must be a group workspace **and** the caller must be a member of that group (`dbentry->getGroup()` + `canFind(user::getGrouplist(), …)`), in addition to the existing `access(R|W|X)` check (so `ws_share`d group workspaces keep working). Caveat: delegates acting purely via a named-user ACL on a *private* workspace can no longer extend it. (c) syslog audit line for foreign extends now names the workspace owner and the acting delegate. (d) `-u` is validated in `commandline()` (rejects leading `-`, `/`, `.`/`..`). Tests: new "ws_allocate -x delegate extend keeps owner's mail" in `bats/test_cap/ws_dash_user.bats` and `bats/test_setuid/ws_dash_user.bats`; man page `-u`/`-m`/`-r`/`-c` wording updated. Existing strings asserted by bats ("you are not owner", "can not be extended") are preserved.*

*Follow-up 2026-10-24 (VM): the membership check in (b) used `user::getGrouplist()` — that is `getgroups(2)`, the kernel-cached supplementary groups of the current login session, which does **not** include the caller's primary group, so delegates whose workspace group is their login group were wrongly denied. Now uses `user::getUserGroupList(username)` (NSS `getpwnam`+`getgrouplist`, primary group included). A `--debug` line logs each condition of the delegate decision (`delegate check by <user>: workspace group=..., caller groups=[...], group member=..., access(...)=...`), and when NSS reports membership but `access()` fails the user gets an actionable hint (new login session / `newgrp` — the running session's kernel credentials can predate a `usermod -G`, which is exactly what had hidden this in the VM). The bats delegate tests now skip unless NSS reports the membership and invoke the tool via `sudo -u "$(id -un)"` so the call carries fresh credentials (plain `newgrp`/`sg` have setgroups/setuid semantics that differ across distros and do not work non-interactively inside bats).*

### M3. Per-filesystem `maxduration` is silently clobbered — **FIXED** (src/config.cpp)

In `src/config.cpp:388-396` the `duration` alias block runs *after* `maxduration`: a filesystem with `maxduration:` but no `duration:` gets reset to 0, then replaced by the (usually larger) global value (`src/config.cpp:398-400`). Admin-set lifetime caps are ignored — workspaces live longer than intended, exactly the kind of policy bug an HPC site won't notice.

*Fix applied: in the (active, yaml-cpp) `Config::readYAML` the block is now `fs.maxduration = 0;` followed by conditional assignments — `maxduration:` is honored, `duration:` remains an alias (still wins when both are present, matching prior behavior), and the 0 → global fallback at the end is unchanged. Added a regression test `config: per-filesystem maxduration and duration alias` in `tests/config_test.cpp` covering all three cases (maxduration-only, duration-alias, neither → global). Note: the dead `WS_RAPIDYAML_CONFIG` branch was already alias-correct and left untouched.*

### M4. ACL evaluation is order-dependent and fails open on typos — **FIXED** (src/utils.cpp, src/config.cpp)

`Config::hasAccess` group loop (`src/config.cpp:469-524`) overwrites `ok` per matching group, so the grant/deny outcome depends on `getgrouplist()` ordering, not config ordering. `parseACL` (`src/utils.cpp:483-513`) silently drops entries failing its regex (e.g. trailing comma) — an intended `-deny` disappears without error; `name:` with empty permission list parses as a full grant.

*Fix applied: (a) `parseACL` (`src/utils.cpp`) now returns a config-ordered vector of `(id, (modifier, intents))` instead of a name-keyed map, logs an error for entries rejected by the syntax regex (they used to vanish silently), and drops an entry whose given permission list contains no valid name instead of letting it silently degrade to "all intents" (which had upgraded `+bob:fin` to a full grant including `admin`); `bob` and `bob:` keep the documented empty-list = all-intents meaning. (b) `Config::hasAccess` (`src/config.cpp`) combines all matching entries deny-wins (AND) instead of "last matching group in `getgroups()`/NSS order wins"; per-entry verdicts are unchanged (so `-y:list` still allows every other intent) and `user_acl` entries still replace the group result. Duplicate ids now combine as AND instead of last-entry-wins. The documented "invalid entry enables access control" trick keeps working — `hasAccess` gates on the raw list size, so malformed entries are logged, never a config-load failure. Rule-evaluation semantics are now documented in `documentation/admin-guide.md` (`user_acl`); regression tests: "hasAccess ACL conflict resolution" in `tests/config_test.cpp` and an expanded `parceACL` section in `tests/utils_test.cpp`. Behavior change to note: sites where a user matched both a `+` and a `-` group previously got an order-dependent (often accidentally granty) result and now consistently get the restrictive one.*

### M5. rapidyaml global error-callback swap is not thread-safe or exception-safe — **DEFERRED** (rapidyaml may go away)

`src/dbv1.cpp:438-458`: `set_callbacks` mutates process-global state, restore is skipped when the throwing handler fires, and `ws_list`/`ws_stat` parse from a thread pool → race/UB. The group-workspace parse at `src/dbv1.cpp:269` (`// FIXME: error check?`) installs no handler at all — a malformed entry file there aborts a setuid tool instead of throwing.

### M6. `ws_restore --delete-data` is broken in both privilege modes — **FIXED** (src/ws_restore.cpp, src/setcap_install.cmake, spec/docker/vm cap definitions)

It raises `CAP_FOWNER` (`src/ws_restore.cpp:303`) but restore's installed permitted set is only `DAC_OVERRIDE+DAC_READ_SEARCH` (`src/setcap_install.cmake:25`) → `cap_set_proc` fails → `exit(1)` (`src/caps.cpp:226-232`). In SUID mode it drops to the user euid, which cannot traverse the 0700 `space/deleted` dir; `rmtree_below` deletes nothing, `remove()` fails ENOTEMPTY (logged only), yet `deleteEntry` still runs (`src/ws_restore.cpp:336-352`) → user data silently orphaned with the DB entry gone. Reconcile the installed cap set with what the code raises, and don't proceed on failed deletes.

*Fix applied: (a) `CAP_FOWNER` added to `ws_restore`'s installed permitted set in all 8 places defining it (`src/setcap_install.cmake`, `hpc-workspace-v2.spec`, `docker/ubuntu-24.04/entrypoint.sh`, `documentation/admin-guide.md`, `prep_cap.sh`, the three `vm/*/Vagrantfile`s and `vm/scripts/rh_run_tests.sh`) — no new privilege class, `ws_allocate`/`ws_release` always had it. (b) The `--delete-data` block now raises `{CAP_FOWNER, CAP_DAC_OVERRIDE, CAP_DAC_READ_SEARCH}` before `rmtree_below` (the 0700 dbuid-owned `space/.removed` needs traversal — the old code raised the DAC pair only *after* the recursion, and the non-delete restore branch at :403 was the intended pattern); in SUID mode the recursion no longer drops to the calling user (`seteuid(getuid())` removed) but runs as root, like `ws_expirer` does. (c) Fail-closed: `cppfs::remove` result is now checked via `std::error_code` + `exists()` — a toplevel that could not be unlinked (e.g. `ENOTEMPTY` after a partial `rmtree_below`, previously silently discarded because the non-throwing semantics were misunderstood) keeps the DB entry, logs an error + syslog line and exits non-zero, so re-running retries. `deleteEntry` failure after successful data deletion likewise exits non-zero instead of reporting success; the SUID `seteuid(dbuid)` hop now happens before `deleteEntry` (for root-squash NFS DBs) but after the toplevel unlink, which runs as root. Tests: extended "ws_restore dash-username with delete-data" in `bats/test_cap/ws_restore.bats` and `bats/test_setuid/ws_restore.bats` to assert the `.removed/<wsid>` directory itself and the DB entry are really gone (the old assertions passed even while the empty directory was orphaned). Note: test environments create `.removed` world-traversable, which is why the old breakage stayed hidden there; real impact required `ws_prepare`-created 0700 dbuid directories. User-mode `bats/test` delete-data tests are unaffected (caller owns everything). `man 1 ws_restore` documents the new keep-entry-on-failure semantics. Verified 2026-10-12: debug build, ctest and bats suites pass.*

*Follow-up 2026-10-24 (VM setuid+capability suites): the 2026-10-12 verification was weaker than it reads — the delete path was never actually executed by any privileged test at that time, so two gaps survived. (1) Test side: both "ws_restore dash-username with delete-data" tests called the human-check-gated `ws_restore`; under bats there is no TTY on stdin, `new_ruh()` gets EOF, `restore()` is silently skipped and the tool exits 0 — `assert_success` passed vacuously. In the VM the two `assert_dir_not_exist` checks also passed vacuously (the `ws_prepare`-created `.removed` is 0700 dbuid-owned and invisible to the bats runner — contrary to the "world-traversable" assumption above; docker is the one that creates it accessible). Both tests in `bats/test_setuid/ws_restore.bats` and `bats/test_cap/ws_restore.bats` now use `ws_restore_notest`, assert the `deleting files as --delete-data was given` output so a no-op cannot pass, and verify `.removed` visibility with `sudo test -e` so they can actually fail. (2) Code side: once the delete really ran, capability mode exposed a residual bug the original fix missed — `ws_restore main()` still called `drop_caps({CAP_DAC_OVERRIDE, CAP_DAC_READ_SEARCH})` before parsing user data, and in caps mode `Cap::drop_caps` *replaces* the process permitted set with exactly its arguments, so `CAP_FOWNER` was gone from the process before `restore()` ever tried to raise it → `cap_set_proc` EPERM → `exit(1)` ("problem raising effective capabilities", `src/ws_restore.cpp:321`). SUID mode was unaffected (`raise_cap` there is `seteuid(0)`), which is why only the cap suite failed. `src/ws_restore.cpp:543` now drops to the full installed set `{DAC_OVERRIDE, DAC_READ_SEARCH, FOWNER}`, matching the `ws_allocate`/`ws_release` pattern and `src/setcap_install.cmake`. Design note: three places must stay in sync per tool — the installed setcap list, `main()`'s `drop_caps` list, and every `raise_cap` in the binary's code paths — with only convention enforcing this; consolidating them (e.g. `drop_caps` defaulting to the binary's own file permitted set) is a worthwhile refactor. Verified 2026-10-24: both privileged bats suites pass 61/61 on the Rocky VM (SELinux enforcing, real `ws_prepare` permissions).*

### M7. Shell quoting in `bin/ws_share` (the share script) and option injection in `bin/ws_extend` — **FIXED** (bin/ws_share, bin/ws_extend, bats/test)

- `WS_PATH=$(ws_find ${CONFIG:+--config $CONFIG} ... $WS_NAME)` (`bin/ws_share:155`) is unquoted and lacks `--`: word-splitting/globbing against the caller's CWD, and option injection into `ws_find` (a `-h` workspace name turns the whole help text into `WS_PATH`; the only validation of `WS_PATH` is "non-empty"). A ghost `${CONFIG_FILE:+--config ...}` hook lets the environment silently redirect config resolution.
- `USERS="$@"` + `for user in $USERS` (`bin/ws_share:174`, same pattern for groups) re-splits and re-globs user lists — `share WS '*'` acts on files in the CWD that happen to be account names.
- `bin/ws_extend:5,10` forwards `"$1"–"$4"` into the privileged `ws_allocate` without `--` (option injection; damage contained by C++-side gates: `--config` root-gated, `-F` validated, duration clamped, `access()` check).
- Neither installed script uses `set -euo pipefail` (mitigated at the mutating sites, which do check `setfacl` exit status); `bin/ws_extend`'s usage path exited 0 — fixed, it now `exit 1`s.

*Fix applied: (a) `bin/ws_extend` now inserts `--` before the forwarded positional arguments in both call forms (`ws_allocate -x -- "$1" "$2"`, `ws_allocate -x -F "$2" -- "$3" "$4"`), so a leading-dash workspace name can no longer be parsed as an option of the privileged `ws_allocate` (`ws_extend -h 3` used to print allocate's help and exit 0). (b) `bin/ws_share` builds the `ws_find` command line from a quoted array plus `--`, the undocumented `CONFIG_FILE` env ghost hook is gone, and `WS_PATH` is now validated as a single absolute path instead of merely non-empty (an injected `-h` formerly made the whole help text the "workspace path"). (c) The `USERS="$@"` / `for user in $USERS` string round-trips (and the `GROUPARG` equivalents, 8 loops total) were replaced by direct `"$@"` iteration — user/group lists are no longer re-split or glob-expanded against the caller's CWD. (d) `set -u` added with `${1:-}` guards for `ACTION`/`WS_NAME` (existing "no action"/"workspace name missing" messages preserved); `basename "$0"` quoted. Deliberately skipped `set -e -o pipefail`: every error check in the script is `if [[ $? -ne 0 ]]`, which `-e` fires through first; converting ~10 sites around an interactive `read` is behavior-risky hygiene better done as a standalone commit — the mutating sites (`setfacl`) already check status and exit 1. Tests: new `bats/test/ws_extend.bats` (5 tests: usage paths + both `--` forwarding forms reject leading-dash names without showing help — the suite never existed before) and 2 regression tests appended to `bats/test/ws_share.bats` (literal `'*'` user must reach the account check un-globbed; `list -- -h` must fail with "Invalid workspace name."). Verified 2026-10-13: both scripts pass `bash -n`/`sh -n`; `bats bats/test` full run shows the identical failure set as HEAD plus the two new tests failing on HEAD and passing on the fix — i.e. zero regressions. (The remaining 10 `ws_share` failures + `ws_send_ical`/`ws_expirer` mail failures on this dev box are environmental: tmpfs `/tmp` group-ACL quirks, read-only `$HOME`, no local SMTP — they pass in CI's ext4+postfix runners.)*

## Low / worth noting

IDs assigned 2026-10-13 for reference; line numbers re-verified against the tree after the H1–H4/M1–M7 fixes (several had drifted).

## Genuinely good (checked, no action needed)

- Privilege discipline is mostly sound: all three privileged tools `drop_caps()` *before* interpreting user input; `raise_cap`/`lower_cap` bracket privileged sections with consistent `SrcPos` tagging; failures `exit(1)` (fail-closed).
- `--config` is consistently gated on root/user-mode across all tools.
- Identity comes from `getpwuid(getuid())`, never `$USER`/`$HOME`.
- The workspace `name` component is regex-restricted (`src/ws.h`), blocking `/`, `..`, NUL, shell metacharacters.
- The `nameTaken()`/`splitExpiredId()`/`renameAsExpired()` path (`src/dbv1.cpp:605-773`) is the model to copy: `symlink_status` existence checks, digit-only timestamp validation, pre-rename collision checks, rollback on failed move.
- `utils::mv` avoids `system()`; no `system()`/`popen()` anywhere in privileged C++ paths.
- The share scripts run `setfacl` as the caller, so kernel ownership enforces "only your own ACLs" regardless of script bugs.
- `ws_editdb`, `ws_prepare`, `ws_validate_config`, `ws_find`, `ws_register` (as deployed, unprivileged): no exploitable findings.
